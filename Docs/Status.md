## Physical iPhone validation

The connected iPhone is an iPhone 16 on iOS 26.4.2. Older crash reports for **0.1.0 (110.1)** and earlier show launch failures because `CLiteRTLM.framework` could not be found; these predate the runpath correction in PR #15. A crash-style resource report for **111.1** records `EXC_RESOURCE` / `PORT_SPACE` after exceeding the per-process limit of 131,072 ports; its triggering stack is in Apple's TextToSpeech framework while creating a run-loop Mach port, which identifies the failure site but does not prove which app object caused the accumulation. On 2026-11-07, USB confirmed **0.1.0 (118.1)** after the user installed the TestFlight update. A USB launch returned PID 1702, but the process had exited within about 12 seconds; the diagnostic ring contained 500 `appLaunch` events, consistent with the previously observed repeated initialization. The user then updated through TestFlight. USB confirmed **0.1.0 (119.1)**, and the learning home appeared on screen. PID 1706 remained alive after a further 20-second observation. The existing diagnostic ring retained old 118.1 records and showed exactly one new `appLaunch` event for 119.1; that event reported process RSS of 109,330,432 bytes and thermal state `fair`. On 2026-11-08, TestFlight installed build **0.1.0 (140.1)** (latest successful upload, run #40); USB confirmed the version, captured the learning home, and observed app PID 2705 still running after 20 seconds. This is startup evidence for that observation window, not long-duration stability or model inference. USB device inspection confirms the phone is paired, Developer Mode is enabled, and a personalized Developer image is mounted.

USB reads, app launch, screenshots, app metadata queries, and WDA accessibility-tree reads work. `pymobiledevice3` is available on the host and reports no USB pairing or Developer image blocker. On 2026-11-08, WDA Runner Build run [42396968692](https://github.com/Guch1120/english_app/actions/runs/42396968692) succeeded, its encrypted IPA was decrypted and validated in Docker, and the signed runner was installed over USB. WDA reports ready and returned the app's accessibility tree, but creating a WebDriver session and sending taps currently hang; interactive controls remain unverified. See [WDA-Automation.md](WDA-Automation.md#device-requirements).

The following specification checks still need physical-device evidence: Pocket TTS and other large model downloads are waiting for the planned tethering window; offline study after model download; Kokoro/Pocket synthesis, rate, cache and interruptions; microphone recording and Parakeet/on-device Apple Speech transcription; transcript comparison and review persistence after restart; Gemma E2B validation, lesson generation and model lifecycle; RE-USE fixed-sample gate and comparison; per-model timing/memory; model error recovery; and thermal/memory behavior. See [TTS.md](TTS.md), [ASR.md](ASR.md), [LLM.md](LLM.md), and [REUSE.md](REUSE.md) for details and safeguards. These checks need functioning interactive device control or a person operating the iPhone.

## Operating and release notes

- Run local tests and quality checks inside Docker with `bash Scripts/test.sh` and `bash Scripts/quality.sh`. Never install the iOS SDK on the Linux host.
- PR CI runs on GitHub macOS for package tests, iOS Simulator build/analyze, unsigned distribution archive checks, and the review gate. App-affecting merges to `main` trigger the protected TestFlight workflow; documentation and unrelated CI-only changes do not. Manual uploads remain available from Actions.
- The short version is **0.1.0**; the latest successful upload is **140.1** from TestFlight workflow run #40. The build number follows `(workflow run number + 100).attempt`. TestFlight automatic updates are controlled by the tester in the TestFlight app; App Store Connect can automatically distribute new builds to an internal group. See [TestFlight.md](TestFlight.md), [Apple's TestFlight automatic-update guide](https://developer.apple.com/videos/play/wwdc2023/10012/?time=52), and [Apple's internal testing guide](https://developer.apple.com/testflight/).
- Signing secrets remain in the GitHub `ios-testflight` environment. Do not commit learning data, audio, model weights, certificates, provisioning profiles, or private keys.
